# SYN-057 routing protocol design — 2026-09-11

## Status

**APPROVED — protocol v2 serialization/binding implementation slice.** The
operator approved stable UUID disclosure, ephemeral local SLO1 selection, and
the absence of runtime-restart continuity promises. This record remains the
architecture boundary: the current slice changes only Link protocol
serialization and binding tests; it does not change daemon routing, the
selection control surface, browser UI, or runtime restart behavior.

The preceding discovery evidence established that current links have no
trustworthy pre-dispatch destination identity. This design separates the two
different routing problems instead of pretending that one field can solve
both:

1. SLO1/JOIN selects a project on the receiving installation locally.
2. SLA2/ANSWER returns to the host project that created the invitation.

## Current wire contracts

All values below are untrusted until the project runtime performs the existing
Link verification. The daemon may later perform bounded structural decoding of
the proposed routing field, but it must forward the original URI unchanged and
must not verify Link signatures.

### SLO1: `synesis://join/SLO1-...`

| Field | Current encoding and issuer | Signed? | Semantic owner | Daemon before dispatch | Survives into SLA2? |
| --- | --- | --- | --- | --- | --- |
| URI scheme/host/path | `synesis://join/SLO1-` plus unpadded URL-safe Base64 | No; structural wrapper | Link parser | Shape only; untrusted | No |

The invitation and traversal offer are independently canonical and signed. The
SLO1 wrapper binds their session, invitation digest, descriptor identity, and
validity interval, but does not add a project identity.

`ControlPlaneHttpHandler` currently parses SLA2 only after a runtime has been
selected, then matches its `sessionId` against retained local pending host
operations. The generated `operationId` is local bookkeeping and is not in the
SLA2 link.

## Current versioning and compatibility facts

- The outer SLO1, SLO1 offer, and SLA2 formats each carry a hard-coded format
  byte `1`. Their decoders reject an unknown format, malformed length, and
  trailing bytes.
- `SessionInvitation` and `TraversalOffer` include their magic, format byte,
  inner `ProtocolVersion`, and all fixed fields in the signed `unsigned` bytes.
  `TraversalAnswer` does the same. Tampering any signed field makes runtime
  verification fail.
- Fields are fixed-order and length-prefixed. There are no optional trailing
  fields, extension map, or tolerant unknown-field mechanism.
- `ProtocolVersion` is a comparable major/minor value and exact-common-version
  negotiation exists for Link transport. The decoders can represent any
  byte-sized major/minor pair, but current onboarding creates `V1`; a parsed
  value is not evidence that the rest of the implementation supports it.
- There is no SLO1/SLA2 downgrade negotiation. An old parser rejects a future
  outer format. A future parser may explicitly accept old format `1`, but must
  not reinterpret it as carrying a target that it does not contain.
- Existing tests cover canonical round trips, unsupported outer versions,
  malformed/truncated payloads, tampering, expiry, and answer-to-offer binding
  in `SessionInvitationTest` and `HumanMediatedLinkTest`.

## Proposed SLO1 recipient-selection contract

The sender may not choose an arbitrary local recipient project. The current
SLO1 has no recipient-project target, and the proposed v2 return target below
names only the host project for the return path.

For an incoming SLO1, the daemon computes bounded local candidates from
`KnownProjectRegistry`:

- A candidate must be a registry entry whose path still passes
  `ProjectApplicationService.require`, whose recorded ID matches the current
  metadata, and whose local user can access it.
- `UNAVAILABLE` and `IDENTITY_MISMATCH` entries are not eligible.
- A candidate may have a live runtime, or be startable through the existing
  explicit project-runtime launcher. No filesystem crawl or process-name scan
  is permitted.
- Duplicate live runtime instances for one stable project ID are ambiguous;
  the daemon may not select by PID, port, age, or map order.
- The daemon decides candidate eligibility and starts/reuses a selected
  runtime. The UI presents candidates and records the local user's explicit
  choice. The selected runtime performs all SLO1 parsing, signature, expiry,
  peer, replay, and Link admission checks.

Result contract:

```text
0 eligible projects       -> URI_UNRESOLVED
1 eligible project        -> select it; start/reuse if needed; dispatch SLO1
2+ eligible projects      -> PROJECT_SELECTION_REQUIRED with bounded candidates
explicit stale selection  -> STALE
runtime Link rejection    -> URI_REJECTED with the runtime authority code
```

An ambiguous selection uses an ephemeral, one-shot daemon selection challenge:
the challenge binds the original URI digest, candidate IDs, and expiry. The
second authenticated local request supplies the challenge and selected stable
project ID. The raw URI is not persisted. A daemon restart invalidates the
challenge and requires the user to resubmit the link. This is explicit
per-invitation selection, not a persisted current-project preference.

### Selected-project persistence decision

The proposed contract chooses **ephemeral explicit selection (A)**. A persisted
current project would make a copied link silently change destination after a
restart, creates stale-selection risk after project moves/removal, and is a
separate generic UI/navigation concern. A persisted default plus override adds
state without helping cryptographic Link routing. A local user can explicitly
select a project for each ambiguous SLO1.

## Proposed SLA2 return-target contract

### Chosen shape

Use a stable host project UUID plus the already present `sessionId`, not a new
opaque handle:

```text
ReturnTarget {
    returnTargetFormat: 1
    returnProjectId: UUID
}
```

For SLO1 v2, `ReturnTarget` is mandatory in the host-signed traversal offer.
`returnProjectId` is the project that created the invitation, not the project
on the recipient installation. For SLA2 v2, the joiner copies the exact
`ReturnTarget` into the responder-signed answer. The existing session ID and
offer digest bind it to one invitation/answer exchange.

The daemon may structurally decode `returnProjectId` and `sessionId` to select
one known project runtime, but it forwards the untouched SLA2 URI. The selected
runtime must verify:

1. the responder signature and descriptor;
2. the answer against the exact stored offer/session;
3. the copied return target against the offer;
4. that the target project ID equals its own project ID; and
5. expiry, replay, identity, and all existing Link rules.

Routing selects a candidate. It never authorizes an answer or mutation.

### Stable project ID versus opaque handle

| Option | Result | Decision |
| --- | --- | --- |
| Signed stable project ID + session | Registry lookup is reconstructable after daemon restart; survives path rename if registry supports an explicit validated relocation; no new route table or runtime registration; leaks a random stable UUID | **Recommended for the smallest slice** |
| Opaque random handle | Hides stable project correlation, but needs a bounded route registry and a runtime-to-daemon registration path; restart and stale cleanup become additional authority-adjacent state | Rejected for the first contract unless the operator treats UUID disclosure as unacceptable |
| Unsigned `projectId` query or JSON hint | Spoofable and not bound to the Link exchange | Rejected |
| Exact runtime endpoint/PID/port | Ephemeral, leaks local process state, fails on restart, and creates unsafe winner selection | Rejected |

The UUID is not a secret, contains no path/name, and is already a durable local
project identity. However, putting it on the wire permits cross-link correlation.
The operator must approve that trade-off or require the more complex opaque
handle design.

## Lifetime, restart, and move semantics

The stable-ID proposal has no daemon routing-handle table. Target lifetime is
the existing invitation/answer validity interval. The daemon stores no Link
secret, raw link, command credential, or membership state.

### Daemon restart

The daemon can reconstruct `returnProjectId -> known project path` from the
validated registry. If the project runtime is live, it can route to that
runtime. If it is absent but the project is still valid, the daemon may start
the existing runtime and forward the answer. This does **not** claim successful
completion: current pending host operations are in-memory in
`ControlPlaneHttpHandler`, so a runtime restart can still produce
`OPERATION_NOT_FOUND`/`URI_REJECTED`. No protocol design may invent operation
continuity that the current runtime does not persist.

### Runtime restart

The target is project A generally, not exact runtime R1. R2 is a valid routing
candidate only if the project identity is valid and exactly one runtime is
eligible. Current R2 cannot recover R1's retained host operation; successful
continuity requires a separately designed durable Link-operation task. The
fail-closed result is preferable to routing an answer to an unrelated project.

### Project move or rename

The target is the stable project UUID, never the path. Current
`KnownProjectRegistry` rejects an existing ID observed at a different path as
an identity mismatch; it has no authenticated relocation operation. Therefore
a move/rename is `STALE`/`URI_UNRESOLVED` until an explicit validated registry
relocation is implemented. The daemon must not crawl for the project or
silently rebind the ID to a new path.

## Versioning and compatibility proposal

Use an explicit new link-format version rather than adding optional bytes to
format 1:

- SLO1 outer wrapper: format `2`.
- SLO1 traversal offer: format `2`, with mandatory signed `ReturnTarget`.
- SLA2 answer: format `2`, with mandatory signed copied `ReturnTarget`.
- Nested `SessionInvitation` remains format `1` because its fields do not
  change.
- Inner Link `ProtocolVersion` remains `V1`; this proposal changes the
  copyable-link envelope, not the transport protocol generation.
- The new target fields are part of the signed unsigned bytes. There is no
  unsigned query parameter, extension map, or silently optional field.
- New parsers accept v1 and v2 explicitly. v1 produces no return target and
  never receives automatic multi-project return routing.
- Old parsers reject v2 as unsupported. They must not be given a v2 link unless
  an explicit compatibility-mode v1 link is intentionally generated.

| Host | Joiner | SLO1/SLA2 result with the proposal |
| --- | --- | --- |
| old | old | v1 works as today; multi-project return routing remains ambiguous/selection-based |
| old | new | v1 is consumable; new joiner returns v1 without inventing a target |
| new | old | v2 is not consumable by the old joiner; explicit v1 compatibility mode is required and loses automatic return routing |
| new | new | v2 carries the signed return target and supports deterministic host-project routing |

Downgrade behavior is explicit: stripping or changing the v2 target changes
signed bytes and invalidates the host or responder signature. A copied old v1
link is a distinct weaker routing case, not a v2 link with a missing optional
field. The daemon may fall back to explicit local selection for v1; it may not
silently choose a runtime or change Link authorization.

## Failure vocabulary

Reuse existing codes where possible and add only the one selection outcome:

| Condition | Result |
| --- | --- |
| malformed/oversized URI or payload | `URI_INVALID` / `URI_UNSUPPORTED` |
| no eligible local project | `URI_UNRESOLVED` |
| multiple eligible SLO1 recipient projects | `PROJECT_SELECTION_REQUIRED` |
| selected project missing, mismatched, or removed | `STALE` |
| v2 SLA2 target project unknown | `URI_UNRESOLVED` |
| v2 SLA2 target known but unavailable/stale | `STALE` |
| legacy v1 SLA2 with multiple possible host projects | `URI_AMBIGUOUS` or explicit selection |
| duplicate eligible runtimes for one project | `URI_AMBIGUOUS` |
| no live runtime after allowed start/reuse | `URI_UNRESOLVED`/`STALE` |
| runtime rejects Link verification, replay, or operation match | `URI_REJECTED` with existing runtime authority code |

## Authority ownership

| Responsibility | Owner |
| --- | --- |
| SLO1/SLA2 wire fields, canonical bytes, signatures, format parsing | `link` protocol classes |
| ReturnTarget creation and binding to host invitation | Host project runtime / `ControlPlaneLinkOperations` through Link onboarding |
| ReturnTarget copying and answer signature | Join project runtime / Link onboarding |
| Local SLO1 candidate selection and one-shot selection challenge | Daemon plus authenticated local UI/CLI selection |
| Stable project ID/path validation | `KnownProjectRegistry` and `ProjectApplicationService` |
| Runtime start/reuse and endpoint liveness | Daemon |
| Full Link verification, replay, identity, membership, and operation state | Selected project runtime / `ControlPlaneLinkOperations` |
| Coordination and project authority | Project runtime |

## Proposed transition graph

```text
HOST PROJECT A
  invite()
    -> host runtime creates signed v2 SLO1 with returnProjectId=A
    -> browser/user transfers SLO1

RECIPIENT INSTALLATION B
  OPEN_URI(SLO1)
    -> daemon computes validated local candidates
    -> zero: URI_UNRESOLVED
    -> one: select/start that project
    -> many: PROJECT_SELECTION_REQUIRED
    -> selected runtime verifies full SLO1
    -> join operation creates SLA2 v2 copying returnProjectId=A

HOST INSTALLATION A
  OPEN_URI(SLA2)
    -> daemon structurally reads returnProjectId=A and sessionId
    -> registry resolves A; no broadcast and no signature decision
    -> exactly one A runtime is selected/started
    -> untouched SLA2 is forwarded to A
    -> A runtime verifies signature, offer/session, target A, expiry, replay,
       identity, and operation state
    -> only then can existing Link completion proceed
```

## Threat and failure analysis

| Case | Daemon behavior | Runtime behavior |
| --- | --- | --- |
| forged unsigned project hint | Ignore/reject; never route from it | N/A |
| modified signed target | May produce only a bounded candidate hint; no broadcast | Signature/offer-target mismatch rejects; no mutation |
| valid target from another invitation/project | Route only to named candidate if locally known | Session/offer/operation/project checks reject |
| handle/UUID from another installation | Unknown local target -> unresolved | No runtime receives it |
| expired target/link | Return stale optimization; preserve runtime check | Expiry verification rejects |
| replayed SLA2 | May route to the named project | Existing operation/replay checks reject |
| v2 downgraded to v1 | Treat as legacy link; require explicit selection if ambiguous | Existing v1 verification remains unchanged |
| malicious joiner reflects arbitrary target | Target is signed/bound in v2 offer and answer | Runtime verifies copied target against stored offer |
| registry tampering | Can cause misrouting/availability loss only | Final project/operation/signature checks prevent authorization bypass |
| daemon crash | Reconstruct stable project lookup from registry | Current in-memory operation may be stale; fail closed |
| runtime crash | Start/reuse at most the named project | Current retained operation may be absent; reject safely |
| copied project ID correlation | Reveals stable random UUID only, not path/name/secret | No authorization follows from disclosure |
| ambiguous runtimes | Explicit ambiguity; never first/last/PID/port winner | No unrelated runtime receives capability-bearing input |

The routing value is not a capability. Possession can at most select a
candidate runtime; it cannot authorize Link acceptance, membership, commands,
browser bootstrap, or project mutation.

## Proposed implementation acceptance criteria

These are criteria for a future implementation slice, not claims of current
implementation:

1. Two host projects are known and active; v2 invitation from A carries only
   the signed host return target A, and the remote sender cannot choose the
   recipient's local project.
2. Multiple recipient projects require explicit local selection; one candidate
   remains compatible with automatic routing.
3. A v2 SLA2 reaches only project A; project B receives no request.
4. Unknown, stale, duplicate, malformed, expired, tampered, replayed, and
   downgraded cases fail closed.
5. Daemon restart reconstructs stable project lookup without retaining Link
   secrets; runtime restart does not falsely claim operation continuity.
6. Path move/removal does not silently rebind a project identity.
7. Old links preserve old Link behavior and lose deterministic multi-project
   return routing explicitly rather than silently guessing.
8. Link verification, replay, membership, and mutation authority remain in the
   selected project runtime.
9. No filesystem crawl, OS protocol registration, membership authority,
   controlled-NAT, hosted service, or broad project-selection UI is included.

## Proposed test matrix before implementation

- Protocol serialization: v1 golden round trips; v2 canonical round trips;
  signed target coverage; missing/trailing/oversized/unknown-version fields.
- Binding: target modified, target copied from another invitation, wrong
  project ID, wrong session, wrong offer digest, and wrong responder.
- Selection: zero/one/multiple valid projects; unavailable/mismatched paths;
  one-shot selection challenge; stale selection; duplicate runtime instances;
  registry-order independence; no filesystem crawl.
- SLA2 routing: A/B correct target, unrelated runtime receives nothing,
  unknown target, stale target, expired target, v1 no-target fallback, and
  daemon restart.
- Runtime restart: R1 exits, R2 starts, route resolves to A, and current
  in-memory operation absence yields safe rejection rather than a false success.
- Security: forged unsigned hint, modified signed target, replay, random
  target, cross-install target, registry tampering, downgrade, and malicious
  joiner reflection.
- Compatibility: old/old, old/new, new/old, new/new matrix above.
- Installed acceptance: two projects, separate authenticated runtime command
  credentials, correct-target-only dispatch, and process cleanup.

## Decision status

**APPROVED.** The operator approved the following decisions for SYN-057:

1. A stable random project UUID is exposed inside the signed v2 return target.
2. SLO1 local selection is ephemeral, authenticated, one-shot, and non-
   persistent; its daemon/UI seam is deferred to a later slice.
3. Runtime restart does not promise pending-Link operation continuity; durable
   operation restoration is a separate task.

The approved protocol implementation is recorded separately in the SYN-057
session evidence and is limited to v2 serialization, signature coverage,
cross-envelope binding, compatibility, downgrade, and transplant tests.
